## T-8.1 Outbox-поллер: итерация по тенантам — **L**

**Зависит от:** T-3.2, T-5.2, T-1.2.
**Файлы:** `src/Cheetah.Core.Outbox/` (поллер/диспетчер), Mongo-эквивалент в
`Cheetah.Core.Mongo` (OutboxStore).

**Проблема.** Outbox-таблица живёт в БД модуля ⇒ в мультитенантном режиме у КАЖДОГО тенанта
свой outbox. Поллер, работающий в хост-скоупе, видит только хостовую БД (или падает).

**Шаги:**
1. Поллер получает `ITenantStore` + `ICurrentTenant`. Цикл опроса:
   - проход «хост»: `Change(null)` → опросить outbox по дефолтной строке (безтенантный
     режим и host-модули) — текущее поведение;
   - для каждого активного тенанта: `Change(tenantId)` → опросить outbox тенантной БД.
     `NullTenantStore` возвращает пусто ⇒ в безтенантном хосте поведение НЕ меняется.
2. Интервал/бюджет: тенантов может быть много — батч-обход с ограничением параллелизма
   (2–4) и per-tenant курсором; выдерживать общий период опроса (опция).
3. Публикуемые из outbox события уже несут `TenantId` в payload ([T-3.2](stage-3-events.md#t-32)) —
   дополнительного стемпинга не нужно; но диспетчер оборачивает публикацию в
   `Change(row.TenantId)` для корректности downstream-хендлеров InMemory-шины.
4. То же — Inbox (идемпотентность консюмеров) и Saga-стор, если поллеры есть.
5. Тесты: события двух тенантов из двух БД доставлены, контексты не перепутаны; хост-outbox
   работает как раньше.

**DoD:** outbox работает в обоих режимах; README Outbox обновлён схемой обхода.

## T-8.2 Тенант-префикс в ключах кэша — **M**

**Зависит от:** T-1.1.
**Файлы:** `src/Cheetah.Core.Cache/` (место нормализации ключей — найти по коду;
если нормализатора нет, ввести `ICacheKeyNormalizer`).

**Шаги:**
1. Нормализатор: `IsAvailable` → `t:{tenantId}:{key}`, иначе `key` как сейчас.
   Внедрить в ЕДИНОЙ точке (реализация `ICacheService`/`IDistributedCache`-обёртки), а не
   по потребителям.
2. Провести ревизию потребителей кэша на предмет обхода единой точки: FeatureManagement-реплика,
   CustomFields-дефиниции, Catalog-цены, `TenancyTenantStore` (тот — хост-скоуп, ему
   префикс НЕ нужен: явный opt-out флагом `hostScoped: true` в API кэша).
3. Тесты: два тенанта пишут под одним логическим ключом → два физических ключа; хост-ключ
   без префикса; opt-out работает.

**DoD:** межтенантное протекание через Redis-кэш исключено на уровне инфраструктуры.

## T-8.3 Проброс тенанта в межсервисных вызовах — **M**

**Зависит от:** T-1.1, T-7.1.
**Файлы:** `src/Cheetah.Backend.ServiceAuth` (M2M `DelegatingHandler`),
`src/Cheetah.Backend.UserAuth` (проверить, ничего не делать), gRPC-инфраструктура
(`Cheetah.Backend.Grpc` — интерцептор).

**Шаги:**
1. On-behalf-of (`UserTokenForwardingHandler`): тенант едет в JWT-клейме — изменений нет,
   покрыть тестом.
2. M2M (`ServiceAuth`): в исходящий `DelegatingHandler` — если `ICurrentTenant.IsAvailable`,
   добавить `X-Tenant-Id: {id}`. На принимающей стороне заголовок принимает
   `HeaderTenantResolveContributor` ([T-7.1](stage-7-aspnetcore.md#t-71)) только для service-токенов.
3. gRPC: клиентский интерцептор — metadata `x-tenant-id`; серверный — тот же механизм
   контрибьюторов (или отдельный gRPC-контрибьютор, если пайплайн другой — посмотреть,
   как `Cheetah.Backend.Grpc` интегрирован с HTTP-middleware).
4. Тесты: Client-библиотека (пилот Deals.Client) в тенант-контексте шлёт заголовок;
   сервер восстанавливает контекст.

**DoD:** тенант не теряется на границе сервисов ни в одном из трёх транспортов
(user-JWT / M2M HTTP / gRPC).
